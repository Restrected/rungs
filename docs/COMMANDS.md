# rungs 1.0.1: command reference

_Generated by `scripts/render-docs.py` from the tool's own `--help`. Do not edit by hand._

```
usage: rungs [-h] [--version] [-C DIR] command ...

File-based tickets for a crew of agents of different skill levels. Tickets are rungs on a ladder (very-low, low, medium, high, xhigh); an agent only takes the rungs it can reach. See .rungs/AGENTS.md.

positional arguments:
  command
    create         create a ticket
    ready          triage -> open
    claim          take an open ticket
    release        give a ticket back to open
    reassign       director only: move a ticket to another agent
    note           add an attributed note
    block          mark a ticket stalled
    unblock        clear a block
    shelve         park a ticket
    unshelve       put a parked ticket back on the board
    submit         hand work in for review
    review         accept or return a submitted ticket
    close          close a ticket
    reopen         reopen a closed ticket
    set            change a ticket field or section
    depend         add or clear a dependency
    list           list tickets
    next           what this agent should work on next
    board          every open ticket grouped by status
    show           print one ticket file
    search         search titles, tags and bodies
    deps           what a ticket waits on and what waits on it
    log            the event log
    stale          claims with no activity for a while
    triage         tickets waiting to be made ready
    agents         the roster and what each agent holds
    whoami         this agent's level, role and workload
    verify         check a change set against a ticket's scope
    doctor         check the store and repair what is unambiguous
    plan           plan files: new, list, show
    cut            create the tickets a plan lists
    intake         turn the files in .rungs/inbox/ into tickets
    request        file one request from the command line instead of writing a JSON
                   file
    import-arbite  convert an existing .arbite/ store into rungs tickets
    init           create .rungs/, rungs.yaml and the generated docs in this directory
    deploy         put rungs on the PATH (or vendor it) and initialise a project
    docs           regenerate .rungs/AGENTS.md and the agent file headers

options:
  -h, --help       show this help message and exit
  --version        show program's version number and exit
  -C DIR           run as if started in DIR
```

## `rungs create`

```
usage: rungs create [-h] [--agent ID] [--json] [--title TITLE]
                    [--kind {design,implement,fix,review,check,research,doc,chore}]
                    [--skill SKILL] [--domain DOMAIN] [--epic EPIC]
                    [--priority PRIORITY] [--tags TAGS] [--scope SCOPE]
                    [--depends-on DEPENDS_ON] [--goal GOAL] [--decisions DECISIONS]
                    [--constraints CONSTRAINTS] [--acceptance ACCEPTANCE]
                    [--evidence-required EVIDENCE_REQUIRED] [--body-file BODY_FILE]
                    [--from-json FROM_JSON] [--triage]

Create one ticket. --title, --kind and --skill are required (or supplied by --from-json). The skill level is the lowest level of agent that can work it, not its urgency.

options:
  -h, --help            show this help message and exit
  --agent ID            acting agent id (company.model.instance); default:
                        $RUNGS_AGENT. Required: the event log and the notes say who
                        did what.
  --json                machine-readable JSON on stdout
  --title TITLE         one line, what the ticket is
  --kind {design,implement,fix,review,check,research,doc,chore}
                        what sort of work this is
  --skill SKILL         lowest level that can work it: very-low, low, medium, high,
                        xhigh
  --domain DOMAIN       routing hint, e.g. ui, python, security
  --epic EPIC           grouping label
  --priority PRIORITY   integer, lower is more urgent, or 'none'
  --tags TAGS           comma separated search labels
  --scope SCOPE         comma separated paths the ticket may change (a trailing / is a
                        directory, * and ** are globs)
  --depends-on DEPENDS_ON
                        comma separated ticket ids that must close first
  --goal GOAL           the Goal section
  --decisions DECISIONS
                        the Decisions already made section
  --constraints CONSTRAINTS
                        the Constraints section
  --acceptance ACCEPTANCE
                        the Acceptance criteria section
  --evidence-required EVIDENCE_REQUIRED
                        the Evidence required section
  --body-file BODY_FILE
                        a markdown file whose '## ' headings fill the sections
  --from-json FROM_JSON
                        a JSON object with the same keys as these options
  --triage              create it in triage/ instead of open/
```

## `rungs intake`

```
usage: rungs intake [-h] [--file F] [--dry-run] [--delete] [--quiet] [--json]

Read every *.json and *.md file in .rungs/inbox/ (oldest first), validate and
sanitise it, and create one ticket per request. The source must be listed under
intake.sources in rungs.yaml. A request whose origin (source:key) is already in the
store is a duplicate and creates nothing; a request that fails validation is
'invalid' and creates nothing. New tickets land in triage/ unless the source is
marked 'ready: true' and the request carries acceptance criteria. Each processed
file is moved to inbox/done/ with a <name>.result.json beside it that says what
happened, so the producer can read the outcome. The run exits 0 whenever it worked:
an invalid request is an outcome, not an error.

Scheduler line:
    */5 * * * * cd /path/to/project && rungs intake --quiet

options:
  -h, --help  show this help message and exit
  --file F    process only this file
  --dry-run   print the outcomes and change nothing
  --delete    delete each processed file instead of moving it to inbox/done/
  --quiet     print nothing on success
  --json      machine-readable JSON on stdout
```

## `rungs request`

```
usage: rungs request [-h] --source NAME --key KEY --title TEXT (--goal TEXT |
                     --goal-file F) [--kind K] [--skill S] [--priority N] [--domain D]
                     [--epic E] [--tags a,b] [--scope a,b] [--acceptance TEXT |
                     --acceptance-file F] [--context KEY=VALUE] [--quoted TEXT |
                     --quoted-file F] [--requested-by WHO] [--approved-by WHO]
                     [--defer] [--json]

File a request without writing a file. The options are the JSON intake contract
(docs/INTAKE.md) one for one, and the request goes through exactly the same
validation, sanitising, defaults and duplicate check as a file in the inbox: there
is no second path into the store.

By default the ticket is created straight away and the result printed. The result
record is also written to .rungs/inbox/done/<source>-<key>.json.result.json, exactly
as it is for a file, so a script can read the outcome the same way either way.

With --defer the request is written to .rungs/inbox/<source>-<key>.json instead and
the next scheduled `rungs intake` picks it up. Use it when the caller must not wait,
or may not write into the ticket folders.

Exit codes: 0 the ticket was created (or deferred), 2 the origin is already in the
store and nothing was created, 1 the request was refused (the reason on stderr).

    rungs request --source helpdesk --key cr-8412 \
        --title 'Saving a daily log on a phone does nothing' \
        --goal 'It must save, or say why it cannot.' \
        --context Page=/projects/312/daily-logs/new --context 'Browser=Safari on iOS' \
        --quoted-file /tmp/what-they-typed.txt

options:
  -h, --help           show this help message and exit
  --source NAME        the producer, as listed under intake.sources in rungs.yaml
  --key KEY            the producer's own id for this request; origin is source:key
                       and must be unique across the store
  --title TEXT         one line, 200 characters
  --goal TEXT          what must be true when this is done
  --goal-file F        read the goal from a file
  --kind K             design | implement | fix | review | check | research | doc |
                       chore (default: the source block, then intake.default_kind)
  --skill S            very-low | low | medium | high | xhigh (default: the source
                       block, then intake.default_skill)
  --priority N         integer, lower is more urgent
  --domain D           routing hint, e.g. ui, python, security
  --epic E             grouping label
  --tags a,b           comma-separated; merged with the source block's tags
  --scope a,b          comma-separated path patterns the ticket may change
  --acceptance TEXT    acceptance criteria; with a ready source this also decides
                       whether the ticket lands in open/ rather than triage/
  --acceptance-file F  read the acceptance from a file
  --context KEY=VALUE  one fact about where the request came from; repeatable.
                       Rendered as a bullet list under Goal
  --quoted TEXT        what a person actually typed; written under a heading saying it
                       is their own words, copied as data
  --quoted-file F      read the quoted text from a file
  --requested-by WHO   prefer an id to a name: the file may be committed
  --approved-by WHO    prefer an id to a name: the file may be committed
  --defer              write the request into .rungs/inbox/ for the scheduled intake
                       instead of creating the ticket now
  --json               machine-readable JSON on stdout
```

## `rungs import-arbite`

```
usage: rungs import-arbite [-h] [--dry-run] [--json] [PATH]

Read an arbite store (default: <project>/.arbite) and create one rungs ticket per
arbite ticket, keeping the id, the tags, the priority, the dependencies and the
epic. tier low/medium/high/frontier becomes skill low/medium/high/xhigh; type
bug/feature/refactor/chore/memo/wish becomes kind fix/implement/implement/chore/
doc/implement; status raw becomes triage and the wishlist/ folder becomes shelved
with a 'wishlist' tag. '## Description' becomes the Goal section and '## Notes' is
kept as Notes. Ids already in the rungs store are skipped. The arbite store is only
read, never changed.

positional arguments:
  PATH        the arbite store to read (default: <project>/.arbite)

options:
  -h, --help  show this help message and exit
  --dry-run   print the mapping and write nothing
  --json      machine-readable JSON on stdout
```

                  [--force-docs] [--json]
